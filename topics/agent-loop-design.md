# Topic 02 설계: 주간보고 작성해줘

- 상태: 모션 그래픽 보강 설계(2차). 이 문서는 구현을 변경하지 않는다.
- 대상: [Agent Loop 페이지](../experiments/agent-loop/index.html).
- 원칙: 기존 스킬 섹션의 내용, 다섯 장면, 문서 이동 모션, v1/v2 비교를 유지한다.
- 변경 범위: 스킬 섹션 앞에 요청 전달·입력 준비·첫 출력을, 뒤에 도구 실행부터 최종 응답까지 추가한다.
- 1차 대비 보강: 실행기의 반복 관리, 모델 호출의 구분, 하나의 출력 위치와 분기, 스킬 비교 구간의 경계.
- 독자: 모델과 도구를 들어 봤지만 에이전트의 반복 실행은 익숙하지 않은 독자.
- 문체: 짧은 문장, 명확한 주체, 일관된 용어. ASD-STE100의 원칙을 한국어에 선택적으로 적용한다. 정식 준수율을 주장하지 않는다.

## 1. 핵심 메시지

**실행기는 모델을 호출하고 출력을 확인한다. 출력이 도구 요청이면 도구를 실행하고, 결과를 기록에 추가한 뒤 모델을 다시 호출한다. 출력이 최종 응답이면 사용자에게 전달하고 끝낸다.**

모델은 도구를 직접 실행하지 않는다. 모델은 호출될 때마다 다음 행동 하나를 출력한다. 반복을 시작하고, 계속하고, 끝내는 주체는 실행기다.

독자가 마지막에 답할 질문은 네 가지다.

1. 모델과 실행기는 각각 무엇을 하는가?
2. 도구 결과는 어떻게 모델에 전달되는가?
3. 모델은 왜 추가 조회를 요청했는가?
4. 반복은 언제 끝나는가?

1차 설계의 문제는 세 가지였다.

- 결과 문서가 입력으로 이동하는 것만으로는 **새 호출**이 보이지 않았다. 모델이 켜진 채로 결과를 받아 보는 것처럼 읽혔다.
- 실행기가 반복을 관리한다는 사실이 화면에 없었다.
- 도구 요청과 최종 응답이 다른 장면에 따로 나타나, 같은 판단 지점에서 갈라진다는 구조가 보이지 않았다.

2차 설계는 이 세 가지를 무대의 고정 요소로 만든다. 실행기 단계 표시, 호출 카드, 출력 분기다.

## 2. 동작 모델

화면이 표현해야 하는 실제 흐름이다. 모션은 이 순서를 바꾸거나 생략하지 않는다.

```text
실행기                                   모델
1. 입력 준비  ── 입력 ──────────────▶  2. 다음 행동 하나를 출력
3. 출력 확인  ◀── 출력 ───────────────
   ├ 도구 요청 → 4. 검사·실행 → 5. 요청과 결과를 기록에 추가 → 1로
   └ 최종 응답 → 사용자에게 전달 → 종료
```

| 단계 | 주체 | 하는 일 | 화면 표현 |
|---|---|---|---|
| 입력 준비 | 실행기 | 기본 지침, 도구 정의, 실행 설정, 대화 기록을 모아 입력을 만든다 | 출처별 문서가 호출 카드로 모임 |
| 모델 호출 | 모델 | 입력을 읽고 출력 하나를 만든다 | 호출 카드 잠금, 출력 위치에 문서 생성 |
| 출력 확인 | 실행기 | 출력이 도구 요청인지 최종 응답인지 확인한다 | 출력 분기의 두 출구 중 하나 점등 |
| 검사·실행 | 실행기 | 허용된 도구인지, 인자가 유효한지 검사하고 실행한다 | 요청 문서가 도구 레인으로 이동, 검사 표시, 결과 생성 |
| 결과 기록 | 실행기 | 도구 요청과 결과를 같은 ID로 기록에 추가한다 | 기록 끝에 한 쌍 추가, 완료된 호출 카드가 목록으로 이동 |

반드시 지킬 규칙:

- 호출이 시작되면 그 호출의 입력은 바뀌지 않는다. 결과는 다음 호출의 입력에만 들어간다.
- 기록은 추가만 한다. 이전 요청과 결과를 덮어쓰거나 지우지 않는다.
- 모델의 이전 출력(도구 요청)도 기록에 남는다. 다음 호출은 자신이 요청한 내용과 결과를 함께 받는다.
- 모델 출력은 한 위치에 나타난다. 같은 위치에 도구 요청이 나오기도 하고, 최종 응답이 나오기도 한다.
- 실행기는 정상 종료 외에도 권한 거부, 도구 오류, 사용자 취소, 반복 한도 때문에 멈출 수 있다. 이 페이지는 정상 종료만 애니메이션으로 보여준다. 다른 종료 조건은 실행기 표시와 상세 설명에서 다룬다.
- 실제 구현은 한 출력에서 여러 도구를 요청하거나 병렬로 실행할 수 있다. 이 예시는 한 번에 한 요청만 사용한다.

## 3. 첫 화면과 전체 구조

첫 화면에서 요청 자체가 가장 먼저 읽혀야 한다. 별도의 소개용 랜딩 화면은 만들지 않는다.

| 요소 | 표시 내용 |
|---|---|
| 페이지 식별자 | `Experiment 02 / Agent Loop` |
| 첫 섹션의 주 제목 | **주간보고 작성해줘** |
| 짧은 보조 문장 | `실행기는 모델을 반복해서 호출합니다. 모델은 매번 다음 행동 하나를 정합니다.` |
| 요청의 실행 설정 | `보고 기간 2026-09-28 ~ 2026-10-04 · Asia/Seoul` |
| 첫 시각물 | 사용자 줄의 요청, 비어 있는 실행기와 호출 카드 |
| 다음 섹션의 시작 | 실행기가 입력을 모으기 시작하는 장면 일부 |

제목과 요청 객체에 같은 문구를 사용한다. 별도의 큰 요청 배너를 중복 배치하지 않는다. 보고 기간은 사전에 주어진 실행 설정이다. 모델이 현재 날짜를 보고 추측한 값으로 표현하지 않는다.

```text
A. 주간보고 작성해줘                          요청 도착
B. 실행기가 첫 입력을 준비한다                입력 준비
C. 모델은 보고서 대신 도구 요청을 출력한다     호출 ① · 출력 확인
   [스킬 확대 구간: 기존 다섯 장면 그대로]     ①의 실행부터 ②의 출력까지 + 파일 수정 비교
D. 실행기가 업무 기록을 조회한다              ②의 출력 확인 · 검사·실행
E. 실행기는 결과를 기록하고 모델을 다시 호출한다 결과 기록 · 호출 ③ 시작
F. 모델은 빠진 정보를 다시 요청한다           호출 ③ · 상세 조회 실행
G. 같은 순서가 한 번 더 반복된다              결과 기록 · 호출 ④ 시작
H. 모델은 도구 요청 대신 보고서를 출력한다     호출 ④ · 종료
I. 실행 기록 전체                            완료된 호출 네 개 요약
```

페이지 안의 장 이름은 설계용 A~I가 아니라 짧은 한국어 제목을 쓴다. 기존 스킬 섹션의 01~05는 그 구간 내부 번호로 유지한다.

## 4. 동일한 사례와 데이터

모든 장면에서 같은 업무 ID, 기간, 출처를 유지한다. 아래 데이터는 고정된 예시이며 실제 업무 시스템이나 모델 API를 호출하지 않는다.

| 업무 ID | 업무 | 최초 조회에서 받은 기록 | 최초 조회에 없는 정보 |
|---|---|---|---|
| WORK-17 | 결제 오류 수정 | 10월 2일 완료, 10월 3일 재개, 보고 기준 시점에 진행 중 | 재개 사유, 다음 조치 |
| WORK-21 | 배포 점검표 정리 | 10월 1일 완료, 출처 포함 | 없음 |

추가 조회 `get_work_detail("WORK-17")`의 결과:

- 재개 사유: 특정 결제 수단에서 같은 오류가 다시 발생했다.
- 현재 상태: 수정 작업 진행 중.
- 다음 조치: 다음 주에 재현 테스트를 보강하고 수정안을 검증한다.
- 근거: `WORK-17 / comment-8`, `WORK-17 / plan-3`.

v2 조회는 상태 변경 기록을 이미 요청한다. 따라서 추가 조회는 상태를 다시 확인하는 요청이 아니다. **누락된 재개 사유와 다음 조치**를 가져오는 요청이다. 이 차이를 데이터와 화면 모두에서 지킨다.

출처는 페이지 안의 예시 기록으로 연결한다. 존재하지 않는 사내 URL이나 외부 링크를 만들지 않는다.

메인 흐름의 호출은 네 번, 도구 실행은 세 번이다.

| 호출 | 이번 입력에 새로 추가된 것 | 모델 출력 | 실행기 처리 |
|---|---|---|---|
| ① | 기본 지침, 도구 정의, 실행 설정, 스킬 목록, 사용자 요청 | `read_skill("weekly-report")` | 파일 읽기 → 본문 반환 |
| ② | ①의 요청과 결과 (`weekly-report` v2 본문) | `search_work(기간, 상태 변경 기록 포함)` | 업무 조회 → 2건 반환 (`search-1`) |
| ③ | ②의 요청과 결과 (`search-1`) | `get_work_detail("WORK-17")` | 상세 조회 → 사유·조치·출처 반환 (`detail-1`) |
| ④ | ③의 요청과 결과 (`detail-1`) | 최종 보고서 | 사용자에게 전달 → 종료 |

①~④는 메인 흐름의 호출 번호다. 스킬 확대 구간의 `MODEL CALL 01~03`과 표기 형식을 다르게 둬 혼동을 막는다. 반복 한도는 예시값 `도구 실행 최대 10회`로 표시한다.

## 5. 루프 무대와 시각 문법

### 무대 구성

신규 구간은 하나의 고정 무대를 공유한다. 장면마다 새 그림을 만들지 않고, 같은 객체의 상태만 바꾼다.

```text
사용자 ─────────────────────────────────────────────────
  주간보고 작성해줘                            [응답 도착 위치]
                                                    ▲ 최종 응답
실행기 ───────────────────────     모델 호출 ③ ─────────│──────
  입력 준비 › 호출 › 출력 확인 ›     입력                  │
  검사·실행 › 결과 기록               지침 · 도구 · 설정 · 요청
  도구 실행 2 / 10                   기록  ① 요청+결과
                                         ② 요청+결과
  도구 레인                         출력  [ 출력 문서 ]────┤
   read_skill · search_work                             ▼ 도구 요청
   get_work_detail ◀──────────────────────────────────────┘

완료된 호출  [①] [②]
```

| 영역 | 내용 | 규칙 |
|---|---|---|
| 사용자 줄 | 요청 문장, 응답 도착 위치 | 처음부터 끝까지 같은 위치 |
| 실행기 단계 표시 | 다섯 단계의 가로 진행 표시 | 현재 단계 하나만 강조. 결과 기록 뒤 입력 준비로 되돌아가는 움직임을 보여줌 |
| 반복 카운터 | `도구 실행 n / 10` | 도구를 실행할 때만 증가 |
| 도구 레인 | 도구 이름과 대상 (스킬 파일, 업무 시스템) | 실행 중인 도구만 강조 |
| 호출 카드 | 현재 호출의 입력 목록과 출력 위치 | 활성 카드는 항상 하나 |
| 출력 분기 | 출력 문서 한 개와 두 출구: `도구 요청 → 실행기`, `최종 응답 → 사용자` | 두 출구를 항상 표시. 쓰지 않는 출구는 흐리게 |
| 완료된 호출 목록 | 끝난 호출의 축소 카드 | 내용 고정. 선택하면 그 호출의 입력과 출력을 펼침 |

실행기와 도구는 왼쪽, 모델 호출은 오른쪽에 둔다. 기존 스킬 구간의 왼쪽 파일, 오른쪽 모델 입력 방향을 계승한다.

### 객체와 움직임

| 객체 | 의미 | 움직임 |
|---|---|---|
| 입력 문서 | 지침, 도구 정의, 실행 설정, 요청 | 입력 준비 단계에서 출처 위치에서 호출 카드로 이동 |
| 기록 쌍 | 같은 ID의 도구 요청과 결과 | 결과 기록 단계에서 기록 끝에 추가 |
| 호출 카드 | 한 번의 모델 호출 | 준비 중 → 진행 중(잠금) → 완료(축소되어 목록으로 이동) |
| 출력 문서 | 도구 요청 또는 최종 응답 | 출력 위치에 생성. 도구 요청이면 도구 레인으로, 최종 응답이면 사용자 줄로 이동 |
| 결과 문서 | 도구 실행 결과 | 도구 레인에서 생성. 결과 기록 단계에서 다음 호출 카드로 이동 |

**호출 카드의 잠금이 이 설계의 핵심 표현이다.** 도구 결과가 도착해도 완료된 카드의 내용은 바뀌지 않는다. 결과는 새 카드에 들어간다. 이전 카드와 새 카드를 잠시 겹쳐, 새 입력이 `이전 입력 + 이전 출력 + 결과`라는 것을 비교하게 한다.

모션은 실제 HTML 객체를 대상으로 한다. 작은 점이나 장식용 화살표만 이동시켜 실행을 대신하지 않는다. 모델 내부의 생각을 연출하는 효과(물결, 반짝임, 말풍선)도 쓰지 않는다. 호출 진행 중은 정적인 상태 라벨로 표시한다. 색상만으로 구분하지 않고 `요청`, `결과`, `최종 응답` 라벨을 함께 쓴다.

### 한 회차의 안무

D~E와 F~G는 같은 안무를 반복한다. 반복이 같아 보여야 루프로 읽힌다. 진행률은 해당 구간의 스크롤 진행률이다.

| 구간 | 실행기 단계 | 움직임 |
|---|---|---|
| 0~15% | 출력 확인 | 출력 문서에 종류 라벨 표시. `도구 요청` 출구 점등 |
| 15~35% | 검사·실행 | 출력 문서가 도구 레인으로 이동. `허용된 도구`, `인자 확인` 표시 |
| 35~55% | 검사·실행 | 도구 실행. 결과 문서 생성. 카운터 증가 |
| 55~75% | 결과 기록 | 요청과 결과가 같은 ID로 묶여 기록 끝에 추가. 현재 호출 카드가 축소되어 완료 목록으로 이동 |
| 75~90% | 입력 준비 | 새 호출 카드 생성. 기존 기록과 새 쌍이 카드 입력으로 들어감 |
| 90~100% | 모델 호출 | 새 카드 잠금. 출력 위치는 비어 있음 |

새 출력이 생기는 순간은 다음 장면의 시작으로 넘긴다. 독자는 장면이 바뀔 때 "새 호출이 무엇을 출력했는가"를 본다.

## 6. 섹션별 설계

### A. 주간보고 작성해줘

**배움:** 요청은 먼저 실행기가 받는다. 이 시점에는 보고서를 쓸 근거가 없다.

- 진입 상태: 사용자 줄에 요청이 있다. 실행기와 호출 카드는 비어 있다.
- 화면 문구: `사용자가 주간보고를 요청합니다. 요청은 먼저 실행기가 받습니다.`
- 모션: 제목의 요청 문장이 사용자 줄에 자리 잡는다. 실행기 단계 표시가 나타난다. 업무 기록 영역은 `조회하지 않음` 상태다.
- 종료 상태: 실행기가 요청을 받았다. 모델은 아직 호출되지 않았다.
- 다음 연결: `실행기는 모델에 무엇을 보낼까요?`

### B. 실행기가 첫 입력을 준비한다

**배움:** 모델 입력은 사용자 문장만이 아니다. 실행기가 여러 출처를 모아 만든다.

- 진입 상태: 실행기 단계 `입력 준비`.
- 화면 문구: `실행기는 기본 지침, 사용할 도구, 보고 기간, 스킬 목록, 사용자 요청을 모읍니다. 이 묶음이 첫 번째 모델 입력입니다.`
- 모션: 다섯 문서가 각 출처 위치에서 호출 카드 ①로 차례로 들어간다. 스킬 목록은 이름과 설명만 들어간다.
- 종료 상태: 호출 카드 ① 완성. 업무 기록과 스킬 본문은 입력에 없다.
- 다음 연결: `업무 기록이 없습니다. 모델은 무엇을 출력할까요?`

보고 기간이 없고 추론할 근거도 없다면, 모델이 사용자에게 기간을 물을 수 있다. 이 대안은 상세 설명에 한 줄로 적는다.

### C. 모델은 보고서 대신 도구 요청을 출력한다

**배움:** 모델의 출력은 최종 응답일 수도 있고, 도구 요청일 수도 있다. 실행기가 종류를 확인한다.

- 진입 상태: 호출 ① 잠금. 실행기 단계 `모델 호출`.
- 화면 문구: `모델은 보고서 대신 weekly-report 파일 읽기를 요청합니다. 실행기는 출력이 도구 요청인지 확인합니다.`
- 모션: 0~40% 출력 위치에 `read_skill("weekly-report")` 생성. 40~70% 실행기 단계 `출력 확인`, 출력 문서에 `도구 요청` 라벨 표시. 70~100% `도구 요청` 출구 점등, `최종 응답` 출구는 흐리게 유지.
- 종료 상태: 실행기가 파일 읽기를 실행할 차례다.
- 다음 연결: 스킬 확대 구간의 진입 문구.

선택 이유를 장문의 내부 사고로 연출하지 않는다. 실제 출력인 도구 요청만 보여준다.

### 스킬 확대 구간 (기존 섹션 유지)

**보존 범위:** 현재 스킬 scrolly의 다섯 장면, 비교 설명, 기술 상세, 파일 변경의 경계 설명. 내용·모션·문구를 바꾸지 않는다. 기존 푸터는 페이지 맨 끝으로 옮긴다.

이 구간은 메인 루프의 한 회차를 **확대한 화면**이다. 메인 무대는 화면 밖으로 물러나고, 구간이 끝나면 정해진 상태로 돌아온다.

| 기존 장면 | 메인 루프에서의 위치 |
|---|---|
| DISCOVER | 호출 ① 입력의 스킬 목록 확대 |
| READ | 호출 ① 출력의 검사·실행. 결과는 파일 본문 |
| ASSEMBLE | 결과 기록과 다음 호출. 본문을 받은 모델이 업무 조회를 요청 |
| REVISE | 비교: 작성자가 파일을 수정해도 이미 만든 입력은 바뀌지 않음 |
| RELOAD | 비교: 수정본을 받은 호출에서 조회 조건이 달라짐 |

경계 규칙:

- 진입 문구: `실행기가 파일을 읽는 과정을 확대해서 봅니다. 마지막 두 장면은 파일이 수정됐을 때를 비교합니다.`
- 이탈 문구: `메인 흐름으로 돌아갑니다. 모델은 v2 절차를 받고, 상태 변경 기록을 포함한 업무 조회를 요청했습니다. 이것이 호출 ②의 출력입니다.`
- 메인 기록에는 `① read_skill → weekly-report v2 본문`과 `② search_work 요청`만 남긴다. v1 본문과 v1 조회 요청은 비교용이다. 메인 기록과 카운터에 넣지 않는다.
- 파일 수정은 작성자의 행동이다. 루프의 단계가 아니며, 모델이 학습하거나 파일을 고친 것이 아니다.
- 메인 무대로 돌아올 때 출력 위치에는 `search_work` 문서가 이미 있다. 확대 구간 마지막 장면의 `NEXT TOOL CALL` 객체와 같은 내용을 사용해 연속성을 만든다.

### D. 실행기가 업무 기록을 조회한다

**배움:** 모델은 요청만 한다. 실행은 실행기가 한다.

- 진입 상태: 호출 ②의 출력 위치에 `search_work(기간, 상태 변경 기록 포함)`. 실행기 단계 `출력 확인`.
- 화면 문구: `실행기는 출력이 도구 요청인지 확인합니다. 허용된 도구인지와 인자를 검사한 뒤 업무 기록을 조회합니다.`
- 모션: 한 회차 안무의 0~55%. 요청 문서가 도구 레인으로 이동하고, 검사 표시 뒤 결과 문서(WORK-17, WORK-21)가 생성된다. 카운터 `1 → 2`.
- 종료 상태: 결과는 실행기에 있다. 모델은 아직 결과를 받지 않았다.
- 다음 연결: `조회가 끝났습니다. 모델은 이 결과를 이미 알고 있을까요?`

카운터는 ①의 파일 읽기가 1, 업무 조회가 2, 상세 조회가 3이다. 확대 구간의 비교용 재로딩은 세지 않는다. 권한 검사는 실행기의 책임이다. 스킬 본문이 권한을 주는 것처럼 표현하지 않는다. 실행 중 표시는 예시의 단계이며 실제 지연 시간이 아니다.

### E. 실행기는 결과를 기록하고 모델을 다시 호출한다

**배움:** 결과는 진행 중인 호출에 끼어들지 않는다. 기록에 추가된 뒤 새 호출의 입력이 된다.

- 진입 상태: 실행기에 `search-1` 결과가 있다.
- 화면 문구: `실행기는 요청과 결과를 기록에 추가합니다. 호출 ②는 끝났습니다. 실행기는 이 기록으로 호출 ③을 시작합니다.`
- 모션: 한 회차 안무의 55~100%. 호출 카드 ②가 축소되어 완료 목록으로 이동한다. 새 카드 ③이 같은 자리에 생성되고, ②의 입력과 출력, `search-1` 결과가 쌓인다. ②와 ③을 잠시 겹쳐 새로 추가된 한 쌍만 강조한다.
- 종료 상태: 호출 ③ 잠금. 입력에 WORK-17의 `완료 → 재개` 기록이 있다. 재개 사유와 다음 조치 칸은 `없음`.
- 다음 연결: `보고서에 다시 시작한 이유와 다음 계획을 쓸 수 있을까요?`

완료 기록에 취소선을 그어 삭제하지 않는다. 완료와 재개는 모두 실제 기록이며, 보고 기준 시점의 분류가 진행 중으로 바뀐 것이다.

### F. 모델은 빠진 정보를 다시 요청한다

**배움:** 앞 결과의 내용이 다음 행동을 정한다. 이 순서는 미리 정해진 것이 아니다.

- 진입 상태: 호출 ③ 진행 중.
- 화면 문구: `조회 결과에 재개 사유와 다음 조치가 없습니다. 모델은 WORK-17의 상세 기록을 요청합니다.`
- 모션: 0~30% 입력의 빈 칸 두 개 강조. 30~50% 출력 위치에 `get_work_detail("WORK-17")` 생성, 빈 칸과 요청을 연결. 50~100% 한 회차 안무의 0~55% 반복. 카운터 `2 → 3`.
- 종료 상태: 상세 결과 `detail-1`이 실행기에 있다.
- 다음 연결: `이 결과도 같은 방법으로 모델에 전달됩니다.`

v2 조회는 상태 변경 기록을 이미 포함한다. 추가 조회는 상태를 다시 묻는 요청이 아니라 **빠진 사유와 다음 조치**를 가져오는 요청이다. 결과가 충분했다면 모델은 바로 보고서를 출력했을 것이다. 이 대안을 상세 설명에 한 줄로 적는다.

### G. 같은 순서가 한 번 더 반복된다

**배움:** 루프는 같은 구조의 반복이다.

- 진입 상태: 실행기에 `detail-1` 결과가 있다.
- 화면 문구: `실행기는 상세 결과를 기록에 추가하고 호출 ④를 시작합니다.`
- 모션: E와 같은 안무를 더 짧은 스크롤 구간으로 재생한다. 호출 카드 ③이 완료 목록으로 이동하고, 새 카드 ④에 `detail-1`이 추가된다. 빈 칸 두 개가 실제 값으로 채워진다. 실행기 단계 표시는 `결과 기록 → 입력 준비 → 모델 호출`로 한 바퀴를 돈다.
- 종료 상태: 호출 ④ 잠금. 입력에 보고서에 필요한 상태, 사유, 조치, 출처가 모두 있다.
- 다음 연결: `이번에는 무엇을 출력할까요?`

첫 조회 결과를 새 결과로 덮어쓰는 연출은 쓰지 않는다. 충분한 근거는 이 고정 예시의 조건이며, 일반적인 정확성 보증이 아니다.

### H. 모델은 도구 요청 대신 보고서를 출력한다

**배움:** 출력이 최종 응답이면 실행기는 반복을 멈추고 사용자에게 전달한다.

- 진입 상태: 호출 ④ 진행 중.
- 화면 문구: `모델은 보고서를 출력합니다. 실행기는 출력이 최종 응답인지 확인합니다. 실행기는 보고서를 사용자에게 전달하고 실행을 끝냅니다.`
- 모션: 0~35% 같은 출력 위치에 보고서 문서 생성, 분류와 출처가 차례로 채워짐. 35~55% 실행기 단계 `출력 확인`, 이번에는 `최종 응답` 출구 점등, `도구 요청` 출구는 흐리게. 55~85% 보고서가 사용자 줄의 응답 위치로 이동. 85~100% 실행기 표시가 `종료`로 바뀌고 카운터는 `3 / 10`에서 멈춤.
- 종료 상태: 응답 전달 완료. 이메일 발송이나 업무 상태 변경은 하지 않는다.

최종 문서는 실제 읽을 수 있는 내용으로 구성한다.

```text
주간보고 | 2026-09-28 ~ 2026-10-04

성과
배포 점검표 정리를 완료했습니다. [WORK-21]

진행 중
결제 오류 수정 작업을 다시 시작했습니다.
특정 결제 수단에서 같은 오류가 재발했습니다. [WORK-17 / comment-8]

다음 주 계획
재현 테스트를 보강하고 수정안을 검증합니다. [WORK-17 / plan-3]
```

출처를 선택하면 완료된 호출 목록의 해당 결과가 펼쳐진다. 보고서 작성과 외부 발송을 혼동시키는 보내기 버튼은 넣지 않는다.

### I. 실행 기록 전체

**배움:** 이번 작업은 모델 호출 네 번과 도구 실행 세 번의 기록이다.

- 화면: 완료된 호출 목록을 세로로 펼친다. 각 행은 `새로 추가된 입력 → 출력 → 실행기 처리`이며 §4의 호출 표와 같은 내용이다.
- 마무리 문구: `모델은 매번 다음 행동 하나를 출력합니다. 실행기는 도구 요청이면 실행하고 다시 호출합니다. 최종 응답이면 끝냅니다.`
- 다른 종료 조건: `권한 거부`, `도구 오류`, `사용자 취소`, `반복 한도 도달`을 정적 목록으로 표시한다. 애니메이션 분기는 만들지 않는다.
- 기존 THE BOUNDARY 단락(파일 수정과 학습의 경계)은 이 뒤, 푸터 앞에 둔다.

## 7. 상태와 구현 경계

메인 루프는 기존 스킬 상태 모델과 분리된 결정적 상태 목록으로 만든다. 각 상태는 `call`, `phase`, `record`, `output`, `counter`를 갖는다. 스크롤 위치에서 상태를 계산한다. 이벤트를 누적하지 않으므로, 되감아도 요청이나 결과가 중복 추가되지 않는다.

|---|---|---|---|---:|
| A | 없음 | 대기 | 없음 | 0 |
| B | ① 준비 | 입력 준비 | 없음 | 0 |
| C | ① | 모델 호출 → 출력 확인 | `read_skill` | 0 |
| 스킬 확대 구간 | 메인 무대 정지 | 기존 장면 | 기존 장면 | 0 → 1 |
| D | ② | 출력 확인 → 검사·실행 | `search_work` | 2 |
| E | ② 완료, ③ 시작 | 결과 기록 → 입력 준비 → 모델 호출 | 비어 있음 | 2 |
| F | ③ | 모델 호출 → 검사·실행 | `get_work_detail` | 3 |
| G | ③ 완료, ④ 시작 | 결과 기록 → 입력 준비 → 모델 호출 | 비어 있음 | 3 |
| H | ④ | 모델 호출 → 출력 확인 → 종료 | 최종 보고서 | 3 |
| I | 없음 | 종료 | 사용자에게 전달됨 | 3 |

- [현재 스크립트](../experiments/agent-loop/main.js)의 전역 `.step`, `.scrolly__stage` 선택자는 기존 스킬 컨테이너 안으로 한정한다. 신규 장면을 기존 다섯 장면의 인덱스에 섞지 않는다.
- 확대 구간에 들어가고 나올 때 메인 무대는 각각 C의 종료 상태와 D의 진입 상태로 고정한다.
- 조회 fixture, 호출 표, 보고서의 업무 ID와 출처는 한 곳에서 관리한다.
- 호출 카드의 입력은 상태 목록에서 `이전 입력 + 이전 출력 + 결과`로 계산한다. 화면별로 따로 작성하지 않는다.
- 이번 범위에는 오류 분기 UI, 병렬 도구 실행, 실제 API 연동을 포함하지 않는다.

## 8. 반응형과 접근성

- 기존 모션 속도와 스크롤 진행 감각을 계승한다.
- 신규 구간은 중첩 카드가 아닌 열린 레이아웃과 얇은 구분선으로 나눈다. 호출 카드만 테두리를 가진다.
- 모바일에서는 무대를 세로로 쌓는다. 실행기 단계 표시는 현재 단계 이름과 점 다섯 개의 한 줄로 줄인다. 호출 카드의 기록은 `기록 n쌍`으로 접는다. 도구 레인은 실행 중인 도구 하나만 표시한다. 완료된 호출 목록은 개수로 표시한다.
- 모바일에서도 출력 분기의 두 출구는 유지한다. 이 페이지의 핵심 구조이기 때문이다.
- 320px에서도 요청, 결과, 다음 행동이 구분돼야 한다. 글자를 읽을 수 없을 만큼 축소하지 않는다. sticky 무대가 설명 전체를 가리지 않게 한다.
- 모션 감소 설정에서는 이동 없이 각 장면의 종료 상태를 보여준다. 실행기 단계, 호출 번호, 연결 ID는 유지한다.
- 라이브 알림은 장면 전환 시에만 갱신한다. 예: `호출 ③ · 출력: 상세 조회 요청`.
- 키보드로 완료된 호출 목록, 출처 기록, 기술 상세에 접근할 수 있어야 한다.

## 9. 구현 순서와 완료 기준

1. 루프 무대의 정적 마크업과 상태 목록을 만든다. 기존 스킬 구간의 선택자를 한정하고 모션 회귀를 확인한다.
2. A~C를 연결하고 스킬 확대 구간의 진입을 붙인다.
3. 확대 구간의 이탈과 D~E를 만든다. 한 회차 안무를 이 단계에서 완성한다.
4. F~G에서 같은 안무를 재사용한다.
5. H~I를 만든다.
6. 전체를 데스크톱과 모바일에서 검수한다.

완료 시 반드시 확인할 사항:

- 첫 화면에 정확히 `주간보고 작성해줘`가 주 제목으로 보인다.
- 기존 스킬 다섯 장면, 비교 설명, 문서 도킹, v1 기록 보존이 유지된다.
- 실행기 단계 표시는 항상 한 단계만 강조하고, `입력 준비 → 모델 호출 → 출력 확인 → 검사·실행 → 결과 기록` 순서를 지킨다.
- 활성 호출 카드는 항상 하나다.
- 잠긴 호출 카드의 입력은 이후 장면에서 바뀌지 않는다. 호출 시작 시점과 완료 목록의 내용을 비교해 검사한다.
- 각 호출의 입력은 `이전 입력 + 이전 출력 + 결과`와 같다. 상태 목록 단위 테스트로 검사한다.
- 출력은 한 위치에만 나타난다. ①~③은 `도구 요청` 출구, ④는 `최종 응답` 출구만 점등한다.
- 카운터는 도구를 실행할 때만 증가하고 최종값은 3이다. 비교용 v1 조회와 재로딩은 세지 않는다.
- v1 조회 요청은 실제 실행 결과가 있는 것처럼 표현되지 않는다.
- 업무 조회와 상세 조회 모두 요청 ID와 결과 ID가 대응한다.
- WORK-17의 완료·재개 이력이 보존되고, 최종 보고서에서는 진행 중으로 분류된다.
- 최종 보고서의 다음 주 계획은 `detail-1`에서 가져온다. 모델이 임의로 만든 계획이 아니다.
- 최종 응답 뒤에 새 호출이나 도구 실행이 없다.
- 되감기 시 이전 상태가 복원되고 중복이 생기지 않는다.
- 320, 390, 901, 1440px에서 모든 신규 장면과 기존 READ 장면을 확인한다. 장면 끝뿐 아니라 이동 중과 역방향 스크롤도 확인한다.
- 문서와 결과, 목록과 경로, sticky 무대와 본문, 출처 표시, 출력 분기의 출구 사이에 겹침이 없다.
- 화면만 본 사람 1~2명이 §1의 네 질문에 답할 수 있다. 이해도는 기하학적 배치 검사만으로 통과 처리하지 않는다.

## 10. 결정 필요

1. **확대 구간의 비교 표시.** REVISE·RELOAD 장면이 루프의 단계로 오해될 수 있다. 기본안은 기존 섹션을 그대로 두고, 진입·이탈 문구와 메인 기록으로 경계를 표시하는 것이다. 그래도 혼동되면 장면 번호 라벨만 `04 / 비교 · REVISE`처럼 바꾸는 최소 변경을 제안한다.
2. **메인 기록의 스킬 버전.** 확대 구간은 v1을 먼저 읽고 수정 후 v2를 다시 읽는다. 메인 기록에는 v2만 남긴다. 기본안은 이탈 문구에서 "메인 흐름은 v2 절차로 이어진다"고 밝히는 것이다. 대안은 메인 기록에 `v1 읽음 → 파일 수정 → v2 다시 읽음`을 그대로 남기는 것이다. 더 정확하지만, 파일 수정이 루프의 단계처럼 보일 위험이 있다.
