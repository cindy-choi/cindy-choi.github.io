# Topic 01 설계: Paged Attention

- 상태: 시각화 설계 초안. 실험 페이지 구현은 아직 시작하지 않는다.
- 인덱스: 01번 Token Cost Playground를 Paged Attention으로 교체. 기존 샘플 파일은 당장 삭제하지 않는다.
- 구현 예정 경로: `/experiments/paged-attention/`
- 독자: 토큰과 LLM 생성을 대략 아는 개인 학습자. GPU 커널이나 가상 메모리 사전 지식은 요구하지 않는다.
- 우선순위: **눈으로 이해되는 인과관계 > 직접 조작 > 애니메이션과 스크롤 연출 > 설명문 > 반응형과 운영 수준 안정성.**
- 작업 기준: 데스크톱 1440 × 900 중심. 모바일 전용 재배치, 브라우저별 튜닝, 범용 프레임워크 구축은 이번 설계의 목표가 아니다.

## 1. 무엇을 이해하게 할 것인가

**문맥의 순서와 GPU 메모리의 배치 순서는 같을 필요가 없다.**

PagedAttention은 시퀀스의 KV 캐시를 고정 크기 블록으로 관리하고, 논리 블록과 물리 블록 사이의 주소표를 사용해 비연속적으로 저장된 KV를 읽는 attention 방식이다. 필요한 만큼 할당하고 같은 내용을 공유할 수 있어, 제한된 KV 메모리에 더 많은 시퀀스를 수용할 여지가 생긴다.

스토리: **토큰이 쌓인다 → 메모리가 막힌다 → 연속 배치를 포기한다 → 주소표를 따라 읽는다 → 빈 블록을 다시 쓴다 → 같은 접두부를 함께 쓴다.**

페이지를 닫을 때 아래 세 질문에 그림으로 답할 수 있어야 한다.

1. 빈 메모리가 있는데 왜 새 요청이 들어가지 못할 수 있는가?
2. KV가 흩어져 있는데 attention은 어떻게 원래 문맥을 읽는가?
3. 같은 prompt에서 답을 둘로 갈라 만들 때 무엇을 공유하고 언제 복사하는가?

## 2. Jev에서 가져올 것과 바꿀 것

참고 대상은 초기 기획만이 아니라 [완성된 Jev 페이지](../experiments/jev-system-one/index.html)다.

- 계승: 짧은 질문형 장 제목, 장 사이의 연결 질문, 같은 상태의 여러 표현, 조작 직후 드러나는 결과, 교육용 데이터와 실제 제품 동작의 구분.
- 계승: 흰 바탕과 검은 글씨, 얇은 구분선, 넓은 여백. 기존 공통 팔레트와 제목 서체를 사용한다.
- 변경: 장마다 새로운 차트를 늘어놓기보다 **같은 메모리 보드가 토큰 띠, 물리 블록, 주소표, 공유 그래프로 변한다.**
- 변경: 등장 시 fade-in만 반복하지 않는다. 스크롤은 구조의 분해와 재배치를, 직접 조작은 할당·읽기·해제의 결과를 담당한다.
- 변경: 첫 화면부터 Paged Attention 제목과 실제 KV 보드가 함께 보인다. 별도 소개용 히어로나 장식용 GPU 그림은 두지 않는다.

이 토픽의 대표 시각물은 확률 막대가 아니라 **주소를 가진 KV 블록**이다. 장면이 바뀌어도 요청 A와 물리 블록 P07의 정체성이 유지되어야 한다.

## 3. 공통 화면과 시각 문법

### 화면 골격

첫 화면의 제목은 `Paged Attention`, 부제는 `문맥은 순서대로, 메모리는 흩어져도.`로 잡는다. 제목 아래에서 바로 생성 중인 토큰과 KV 캐시가 보이고, 다음 장의 시작도 살짝 드러난다.

주요 장은 카드 안에 넣지 않는 넓은 실험 무대다. 고정되는 무대의 약 70%는 그림, 나머지는 짧은 질문과 현재 수치에 쓴다. 실험 중 긴 정의나 코드가 그림보다 앞에 나오지 않게 한다.

```text
Paged Attention                     03 / Block Table

요청 A의 토큰      t0 t1 t2 t3 | t4 t5 t6 t7 | t8 t9
논리 블록         L0          | L1          | L2
                       주소표: 0 → 7, 1 → 2, 2 → 10

GPU KV 풀         P00  P01  P02  P03
                  P04  P05  P06  P07
                  P08  P09  P10  P11

현재 선택         token 6 → L1 / offset 2 → P02 / offset 2
```

그리드는 물리 블록 ID를 보기 쉽게 줄바꿈한 것이다. 행이 다르다고 별도 GPU이거나, 그림상 가까운 칸이 실제 CUDA 접근 패턴을 뜻하는 것은 아니다.

### 토큰과 블록

| 표현 | 의미 | 움직임 |
|---|---|---|
| 토큰 번호 `t0`와 작은 K/V 쌍 | 해당 토큰의 캐시된 key와 value | 새로 처리된 토큰의 쌍만 추가 |
| 내부가 4칸인 블록 | 교육용 기본 블록 크기 B=4 tokens | 할당될 때만 테두리가 나타남 |
| `L0`, `L1` | 시퀀스 안의 논리 블록 순서 | 토큰 띠 아래 고정 |
| `P07`, `P02` | KV 풀 안의 물리 블록 ID | 할당 후 위치와 ID 고정 |
| A: amber, B: magenta, C: 검정 윤곽 | 요청 또는 분기 소유권 | 색과 문자 라벨을 항상 함께 사용 |
| 중립 회색 채움 + 문자 라벨 | 그 장의 초점이 아닌 배경 요청 (Act 2의 A·C·E 등) | warm 색은 장당 최대 2개 소유권에만 사용 |
| 회색 사선 | 할당됐지만 아직 유효 토큰이 없는 슬롯 | 유효 KV가 생기면 사라짐 |
| 빈 윤곽선 | 아직 누구에게도 할당되지 않은 블록 | 할당 시 소유권 색 부여 |
| 여러 연결선과 `refs: 2` | 공유된 물리 블록 | 참조 추가·해제 때 숫자와 선 변경 |

한 칸은 문자나 토큰 문자열 자체가 아니라 **그 토큰에 대응하는 KV 저장 용량**이다. 실제 K/V는 여러 layer와 KV head의 텐서이며, 그림은 이를 한 슬롯으로 묶은 개념도다. K와 V의 실제 메모리 배열이 그림처럼 붙어 있다는 뜻은 아니다.

본문은 흑백, 색은 소유권과 현재 접근 중인 경로에만 사용한다. 모든 토큰에 무지개색을 주거나 블록을 구별하려고 매번 색을 바꾸지 않는다. 실험 영역 뒤에서는 기존 배경 효과를 약하게 하거나 가린다.

## 4. 장별 스토리보드

### Act 1. 답이 길어질수록 무엇이 남을까?

**한 가지 배움:** 출력 문장은 늘어나고, 이미 처리한 토큰의 KV는 다음 decode에서 재사용된다.

- 시작 화면: 위에는 prompt 4토큰, 아래에는 토큰 번호가 맞춰진 K/V 쌍. 모델 가중치는 옆의 작은 고정 라벨로만 구분한다.
- 스크롤 0~35%: prompt가 prefill로 처리되며 4개의 KV 쌍이 한 묶음으로 나타난다.
- 35~75%: decode 한 스텝씩 현재 입력 토큰의 KV가 추가되고 query가 유효 문맥을 읽는다. 그 결과 다음 토큰이 나온다.
- 75~100%: 생성된 다음 토큰은 대기 위치에 있고, 다음 스텝에 입력될 때 자기 KV를 얻는다. 생성 즉시 미래 토큰의 KV까지 캐시한 것처럼 그리지 않는다.
- 주 조작: 토큰 스텝 슬라이더. 앞뒤로 움직이면 처리된 문맥, 현재 입력, 다음 출력이 함께 바뀐다.
- 결과: `캐시된 토큰 수` 하나만 표시한다. 아직 블록이 없으므로 슬롯 지표를 따로 두지 않고, 고정 크기의 모델 가중치 라벨과 대비시킨다.
- 연결 질문: **“끝날 길이를 모르는데, 자리는 얼마나 잡아 둬야 할까?”**

문자열은 고정 예시이고 실제 tokenizer는 호출하지 않는다. prefill의 내부 계산 전체나 Q/K/V 생성 행렬을 이 장에서 펼치지 않는다.

### Act 2. 비어 있는데 들어가지 않는다

**한 가지 배움:** 총 여유량과 연속된 여유량은 다르다.

이 장은 외부 단편화만 분리한다. 먼저 아래의 동일한 요청 이력으로 두 보드를 만든다. 아직 최대 길이 선예약 효과는 섞지 않는다.

| 초기 요청 | 물리 블록 | 실제 사용 토큰 |
|---|---|---:|
| A | P00~P02 | 12 |
| B | P03~P04 | 8 |
| C | P05~P07 | 12 |
| D | P08~P09 | 8 |
| E | P10~P11 | 8 |

- 총 12블록 × 4슬롯 = 48슬롯이며 처음에는 전부 차 있다.
- 스크롤 첫 구간에서 B와 D가 완료된다. 해당 블록만 비워지고 나머지 블록은 움직이지 않는다.
- 빈 블록은 4개지만 가장 큰 연속 구간은 2개다. 새 요청 F는 12토큰, 즉 3블록이 필요하다.
- 주 조작: `F 요청 추가`. 왼쪽 연속 할당 보드는 자리를 찾다가 대기 상태가 되고, 오른쪽 paged 보드는 P03·P04·P08에 할당한다.
- 애니메이션: 처음에는 하나의 동일한 보드가 좌우 비교로 펼쳐진다. 같은 F가 양쪽에 도착하고, 오른쪽에서만 연결된 논리 블록 3개가 떨어진 빈칸을 가리킨다.
- 결과: 왼쪽 `여유 16 / 최대 연속 8 / F 대기`, 오른쪽 `F 수용 / 남은 여유 4`.
- 되감기는 두 보드 모두 B와 D의 완료 직후로 돌린다. 한쪽만 초기화하지 않는다.
- 연결 질문: **“흩어 놓으면 원래 순서는 어디에 남을까?”**

연속 할당은 현상을 분리하기 위한 교육용 비교 정책이다. 모든 비-paged 시스템이 반드시 이 정책을 쓰거나 메모리 이동·압축 수단이 전혀 없다는 주장은 하지 않는다.

### Act 3. 순서는 주소표에 남는다

**한 가지 배움:** 토큰 위치는 논리 블록 번호와 offset으로 나뉘고, 주소표가 물리 블록을 찾는다.

- 비교 보드의 오른쪽이 확대되어 논리 토큰 띠 / block table / 물리 KV 풀의 3층으로 펼쳐진다.
- 읽기 예제는 A의 10토큰, B=4, `blockTable = [7, 2, 10]`인 명시적 체크포인트로 전환한다. 이전 요청 F가 갑자기 A로 바뀐 것처럼 연결하지 않는다.
- 주 조작: 토큰 띠에서 위치를 선택하는 스크러버. 선택 토큰, 논리 블록, 주소표 행, 물리 슬롯이 순서대로 강조된다.
- 대표 예: `token 6 → floor(6 / 4) = L1 → table[1] = P02 → offset 2`.
- 스크롤은 처음에는 논리 띠만, 다음에는 주소표, 마지막에는 물리 풀을 공개한다. 이미 할당된 KV를 옮기는 연출 대신 같은 객체를 확대하고 연결선만 드러낸다.
- 결과: token 3→4 경계에서는 offset이 3→0으로 돌아가고 물리 블록은 P07→P02로 바뀐다. 물리 ID는 오름차순일 필요가 없다.
- 마지막 P10에는 t8·t9만 유효하고 나머지 2칸에는 사선이 남는다.
- 연결 질문: **“주소만 찾으면, attention 결과도 같을까?”**

`logicalBlock = floor(tokenIndex / blockSize)`, `offset = tokenIndex % blockSize`, `physicalBlock = blockTable[logicalBlock]`를 그림 아래 한 줄로만 둔다. 블록을 임의로 드래그해 잘못된 매핑을 만드는 퍼즐은 넣지 않는다.

### Act 4. 흩어진 KV를 읽어도 같은 attention이다

**한 가지 배움:** 저장 배치는 달라져도, 같은 Q/K/V와 마스크를 사용하면 같은 attention을 계산한다.

**이 장이 페이지의 중심이다.** 단순히 블록을 나누는 메모리 설명에서 끝내지 않고 이름의 Attention까지 보여준다.

- 시작 화면: 현재 query 하나가 위에 있고, 아래에는 Act 3의 유효 토큰 10개와 흩어진 블록이 있다.
- 스크롤 0~25%: query → 주소표 → P07·P02·P10 순으로 읽기 경로가 켜진다.
- 25~55%: 블록 안의 유효 K를 읽어 토큰 위치별 점수 칸을 채운다. 빈 슬롯은 계산에서 제외된다.
- 55~80%: **전체 유효 문맥**에 대한 softmax 막대가 나타난다. 블록마다 합이 1인 별도 softmax를 만들지 않는다.
- 80~100%: 각 가중치와 V의 기여가 output 벡터로 합쳐진다. 이것은 다음 토큰 확률이 아니라 attention head의 출력이다.
- 주 조작: `연속 저장 / Paged 저장` 세그먼트. 같은 fixture의 별도 저장 배치를 전환하고 출력 수치는 유지된다. 실제 allocator가 KV를 매번 재배열하는 동작으로 표현하지 않는다.
- 보조 관찰: 토큰에 hover하면 주소, Q·K 점수, 가중치, V 기여를 연결해 강조한다.
- 결과: 두 output 벡터와 `최대 절대 오차`를 표시한다. 재생 속도 차이를 성능 비교처럼 보여주지 않는다.

작은 합성 벡터를 사용해 실제로 계산한다. 예: head dimension 2, query `[1, 0]`, 토큰 위치별 고정 K/V. 식은 접힌 상세 영역에 둔다.

$$
o = \sum_{i=0}^{n-1} \operatorname{softmax}\left(\frac{qK^T}{\sqrt{d}}\right)_i V_i
$$

읽기 빛과 작은 점은 접근 순서를 설명하는 표식이다. **전체 KV를 거대한 연속 버퍼로 복사하는 중간 장면은 없다.** 실제 GPU는 병렬로 처리하며, 여기서 한 블록씩 비추는 순서는 교육용이다. 부동소수점 계산 순서에 따른 미세한 차이까지 모든 구현에서 bitwise 동일하다고 약속하지 않는다.

연결 질문: **“필요할 때만 블록을 받으면, 남는 공간은 얼마나 될까?”**

### Act 5. 필요한 만큼 받고, 끝나면 돌려준다

**한 가지 배움:** 블록 단위 증분 할당은 선예약 낭비를 줄이지만, 마지막 블록의 빈 슬롯까지 없애지는 않는다.

- 별도 체크포인트: 요청 A의 현재 길이 5, 최대 예약 길이 12. 선예약 정책은 12슬롯을 잡고, B=4인 paged 정책은 8슬롯을 잡는다.
- 주 조작: 블록 크기 `2 / 4 / 8` 세그먼트. 바꾸면 같은 5토큰을 가진 별도 시뮬레이션으로 다시 구성한다. 실행 중 vLLM의 block size를 즉시 바꾸는 기능이라는 뜻은 아니다.
- B=2: 3블록, 할당 6, 꼬리 빈칸 1. B=4: 2블록, 할당 8, 빈칸 3. B=8: 1블록, 할당 8, 빈칸 3.
- 스크롤 중간: B=4 체크포인트의 5→8→9토큰 성장. 8까지는 기존 블록을 채우고, 9번째 토큰의 KV를 쓰기 전에 새 블록 하나를 받는다.
- 스크롤 마지막: 요청 A 완료 → 참조 제거 → refs가 0인 블록을 free list에 반환 → 대기 중 B가 그 블록을 사용한다. 다른 활성 요청의 KV는 움직이지 않는다.
- 결과: `유효 슬롯 / 할당 슬롯 / 꼬리 빈칸 / 주소표 항목 수`만 표시한다. 작은 블록이 항상 더 빠르다는 점수는 만들지 않는다.
- 연결 질문: **“같은 prompt로 답을 두 개 만들면, 앞부분도 두 번 저장해야 할까?”**

비공유 시퀀스 길이 n에서 할당 슬롯은 `ceil(n / B) × B`, 꼬리 빈칸은 그 값에서 n을 뺀 수다. `0 ≤ 빈칸 < B`이며 길이 0에서는 할당도 0이다. 이 수치는 모델 가중치·주소표·런타임 버퍼를 제외한 KV payload 용량이다.

더 작은 블록은 꼬리 낭비를 줄일 수 있지만 주소표 항목과 관리 비용이 늘 수 있다. 이 장은 메모리 수량을 보여줄 뿐 커널 성능의 최적 block size를 추정하지 않는다.

### Act 6. 함께 읽고, 달라질 때만 복사한다

**한 가지 배움:** 공유는 같은 물리 블록을 가리키는 것이고, 공유 중인 블록에 쓰려 할 때 copy-on-write가 필요하다.

- 시작 체크포인트: B=4, prompt 6토큰이 P03의 4칸과 P09의 2칸에 있다. 아직 단일 시퀀스이며 두 블록의 refs는 1이다.
- 스크롤 0~30%: 동일 prompt의 두 출력 분기 A/B가 생긴다. 주소표 두 개가 같은 P03과 P09를 가리키고 refs가 2가 된다. KV 복사 애니메이션은 없다.
- 30~60%: 마지막 공유 블록 P09를 확대한다. 유효 2칸과 빈 2칸을 함께 보여준다.
- 주 조작: `A 다음 스텝`. A가 첫 continuation 토큰을 입력으로 처리하여 KV를 쓸 때, refs=2인 P09의 유효 KV를 새 P05에 복사하고 A의 매핑만 바꾼 뒤 P05의 offset 2에 쓴다.
- 인과 순서: 새 블록 할당 → 기존 유효 KV 복사 → A의 주소표 갱신과 참조 수 변경 → 새 KV 쓰기. 복사 전에 원본에 쓰는 프레임이 없어야 한다.
- 결과: A는 `[3, 5]`, B는 `[3, 9]`. P03은 refs=2, P05와 P09는 각각 refs=1. B의 기존 KV 값은 그대로다.
- 이후 B가 자기 continuation을 처리할 때 P09는 단독 소유이므로 그대로 쓴다. 모든 토큰마다 복사하는 애니메이션을 만들지 않는다.
- 마지막 스크롤: A가 완료되어도 B가 참조하는 P03은 남는다. B까지 끝나면 반환된다.

보조 프리셋 `prompt 8토큰`에서는 마지막 공유 블록도 가득 차 있다. 새 continuation은 별도 새 블록에 쓰므로 기존의 가득 찬 prefix 블록을 복사할 필요가 없다. 이 대비가 copy-on-write를 단순한 “분기하면 전부 복사”와 구분해 준다.

공유량은 **서로 다른 물리 블록의 개수**로 센다. 6토큰 prompt 분기 직후는 2블록, A의 첫 쓰기 후는 3블록, 시작부터 두 사본을 둔 비교군은 4블록이다. 각 주소표 길이를 더하면 공유 메모리를 이중 계산하므로 그렇게 세지 않는다.

이 장은 같은 prefill 결과에서 갈라진 parallel sampling이다. 서로 다른 요청의 비슷한 문장이 자동으로 공유된다고 설명하지 않는다. 요청 간 automatic prefix caching의 키·적중 정책은 별도 주제다.

마지막 문장: **“순서는 주소표에, KV는 빈 블록에. 같은 앞부분은 함께 읽고, 달라지는 블록만 따로 쓴다.”**

## 5. 스크롤과 직접 조작의 역할

| 장 | 권장 스크롤 길이 | 스크롤이 바꾸는 것 | 사용자가 바꾸는 것 |
|---|---:|---|---|
| 1 | 150vh | prefill과 decode 관점 | 처리 스텝 |
| 2 | 180vh | 비교 보드와 해제된 빈자리 공개 | F 요청 도착 |
| 3 | 170vh | 논리 → 주소표 → 물리의 층 분리 | 조회할 토큰 위치 |
| 4 | 230vh | 읽기 → 점수 → 정규화 → 가중합 | 연속 / paged 저장 비교 |
| 5 | 180vh | 증분 할당 → 완료 → 재사용 | 블록 크기 |
| 6 | 220vh | 분기 → 공유 → 쓰기 → 해제 | 다음 스텝과 경계 프리셋 |

- 각 장은 짧은 진입 문장 뒤 sticky 무대가 고정된다. 스크롤 위치가 설명 단계의 0~1 진행률을 결정하며 문서 자체의 스크롤은 가로채지 않는다.
- 150vh는 150vh 동안 아무것도 안 바뀐다는 뜻이 아니다. 2~4개의 의미 있는 장면에 나누어 쓰고, 그림이 멈춰 있는 긴 구간은 프로토타입에서 줄인다.
- 스크롤용 설명 체크포인트와 사용자가 변경한 실험 상태를 분리한다. 뒤로 스크롤했다고 `allocate`나 `append`를 다시 실행해 중복 할당하지 않는다.
- 주 조작을 만지면 현재 장의 자동 재생은 멈춘다. 스크롤은 카메라·강조를 바꾸되 실험 결과를 덮어쓰지 않는다. reset은 해당 장의 명시적 체크포인트로 돌아간다.
- 재생·일시정지·한 스텝·초기화는 Lucide 아이콘과 짧은 툴팁으로 제공한다. 상시 노출 컨트롤은 주 조작 1개와 작은 재생 도구 묶음으로 제한한다.
- 값이 바뀌지 않는 무한 파티클, 이유 없는 흔들림, 패럴랙스 장식은 넣지 않는다. 읽기는 180~300ms 강조, 할당·매핑은 450~650ms, copy-on-write는 약 1.2초의 단계 애니메이션으로 시작한다.
- 실험의 정상 경로와 수치 일치는 필수지만, 모든 화면 크기와 예외 상황을 방어하는 작업은 미룬다. 모바일 전용 설계는 이번 완료 조건이 아니다.

## 6. 구현 경계

[사이트 아키텍처](../docs/ARCHITECTURE.md)의 state / model / view / interaction 분리를 따른다. 초기 파일은 index.html, 전용 CSS, main.js, data.js 정도로 제한하고 필요해지기 전에 범용 시뮬레이션 엔진을 만들지 않는다.

- 렌더링: DOM/SVG + D3의 keyed join. 수십 개 블록과 연결선이므로 Canvas나 3D는 필요 없다. SVG는 실제 메모리 상태를 표현하는 데이터 도식으로 사용한다.
- 스크롤: CSS sticky와 GSAP ScrollTrigger를 사용해 장별 진행률을 연결한다. 직접 스크롤 엔진을 만들지 않는다. 도입 시 버전을 고정한다.
- 모델: 교육용 allocator와 block table lookup, 작은 벡터의 attention 계산만 구현한다. 실제 GPU 커널, 모델 추론, 서버 API는 실행하지 않는다.
- 데이터: 토큰 ID, KV 벡터, 요청 도착·완료 이벤트를 고정 fixture로 제공한다. 무작위로 보기 좋은 결과를 생성하지 않는다.
- 상태: `blockSize`, `physicalBlocks`, `blockTables`, `sequenceLengths`, `refCounts`, `freeList`, `selectedToken`, `checkpoint`, `playback`.
- 계산: `appendKV`, `allocateBlock`, `releaseSequence`, `forkSequence`, `copyOnWrite`, `resolveToken`, `computeAttention`, `deriveMetrics`.
- 뷰: 동일 physical ID를 동일 요소 key로 유지한다. 해제 후 재할당 때만 소유권을 바꾼다. 주소표·그림·수치는 같은 모델에서 파생한다.

기술적 경계는 긴 경고문을 매번 반복하기보다 해당 도식의 짧은 라벨과 상세 펼침에 둔다. 실제 벤치마크로 오해할 속도계, tokens/sec, GPU 이용률 수치는 넣지 않는다.

## 7. 오해를 막는 기준

1. KV 캐시는 모델 가중치가 아니다. 토큰별 중간 key/value이며 전체 대화 문자열을 저장하는 그림도 아니다.
2. 논리 블록이 물리 블록에 대응한다. 토큰 문자열의 정렬 순서를 바꾸는 알고리즘이 아니다.
3. PagedAttention은 KV를 압축하거나 과거 토큰을 무시하는 sparse attention이 아니다. 이 설계의 dense decode에서는 모든 유효 문맥을 읽는다.
4. 블록을 나누었다고 attention이 블록별 독립 softmax가 되지 않는다. 전체 문맥에 대한 정규화가 필요하다.
5. 마지막 블록의 내부 단편화는 남는다. “낭비 0%”나 “항상 4% 미만”을 일반 법칙으로 쓰지 않는다.
6. 메모리 효율 향상은 더 많은 시퀀스를 수용할 여지를 주지만, 단일 토큰 계산이 같은 배수로 빨라진다는 뜻은 아니다. continuous batching 전체를 PagedAttention과 동의어로 취급하지 않는다.
7. 공유 블록은 읽을 때 복사하지 않는다. 단독 소유가 되었거나 새 블록에 쓰는 경우도 무조건 COW를 하지 않는다.
8. OS paging에서 착안했지만 CPU 디스크 페이지 교환이나 GPU↔CPU offload를 보여주는 것이 아니다.
9. 원 논문의 메커니즘을 설명하는 페이지다. 최신 vLLM의 모든 backend·모델이 이 장면과 동일한 내부 경로를 사용한다고 단정하지 않는다.

## 8. 제작 순서와 완료 기준

### 먼저 만들 프로토타입

**Act 3 + Act 4를 먼저 만든다.** token 6을 선택했을 때 P02의 offset 2가 켜지고, 같은 fixture를 연속 또는 paged 배치로 읽어 같은 output이 나오는지 확인한다. 이것이 이해되지 않으면 앞뒤 장을 늘리지 말고 주소표와 읽기 연출을 고친다.

다음 순서는 Act 2의 실패/성공 비교 → Act 5의 할당·해제 → Act 6의 공유·COW → Act 1 도입과 장 사이 스크롤 연결이다. 끝난 뒤 홈 01번을 실제 실험 페이지 링크로 바꾼다.

### 모델 검증

- Act 2 fixture: 여유 16슬롯, 최대 연속 8슬롯에서 12슬롯 F가 연속 정책에서는 대기하고 paged 정책에서는 수용된다.
- 주소 조회: B=4, table=[7,2,10]에서 t0→P07/0, t3→P07/3, t4→P02/0, t6→P02/2, t9→P10/1.
- 같은 Q/K/V를 사용하는 연속·paged attention 결과가 JS float64 fixture 기준 최대 절대 오차 1e-10 이하다. 유효 길이 밖 슬롯을 다른 값으로 채워도 결과는 변하지 않는다.
- 5토큰의 B=2/4/8 할당 슬롯이 각각 6/8/8이고 꼬리 빈칸은 1/3/3이다. 길이 0과 블록 경계 직전·직후도 확인한다.
- 공유 6토큰 prompt는 분기 직후 고유 물리 블록 2개, A 쓰기 후 3개다. B의 KV는 바뀌지 않고 실제 참조 개수와 refs가 일치한다.
- refs가 남은 블록을 free list로 반환하지 않는다. 완전히 해제된 블록만 재사용하며 동시에 두 독립 요청의 쓰기 대상이 되지 않는다.

### 시각 검증

- 1440 × 900에서 주요 스크롤 체크포인트를 캡처한다. 첫 화면의 제목과 실제 보드, 주소표의 세 층, attention 출력, COW 복사 대상이 즉시 식별되어야 한다.
- 스크롤 역방향으로도 블록이 중복 생성되지 않고, 재생을 멈춰 모든 중간 상태를 관찰할 수 있어야 한다.
- 입력 → 바뀐 주소 또는 소유권 → 결과 수치가 한 화면에서 이어져 보여야 한다. 바뀐 숫자만 있고 이유가 보이지 않으면 미완료다.
- COW 장면에서 복사하지 않는 공통 prefix와 복사하는 마지막 블록이 동시에 보여야 한다.
- 모바일 대응 점수나 운영 환경 부하 테스트 대신 **개념이 실제로 보이는지**를 완료 판단으로 삼는다.
